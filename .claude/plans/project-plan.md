# Plan: To-Do List with React + TypeScript

## Context

The directory `C:\Users\User\Desktop\to-do-list` currently contains only `README.md`, `diary.md` and `.git` — this is a greenfield project (branch `develop`).

We need a project — a task list where the user can:

- add a task;
- delete a task;
- toggle a task between done and not done;
- filter the list: All / Active / Completed;
- come back later and still see their tasks — data is persisted in `localStorage`.

Stack chosen by the user: React, TypeScript, CSS Modules, ESLint, Prettier, localStorage.
Bundler: Vite. No tests. Scope: strictly the requirements above, no extra features.

---

## Libraries and why each one is needed

### Application dependencies (`dependencies`)

| Package | Why |
|---|---|
| `react` | The UI library itself: components, state, hooks. |
| `react-dom` | A separate package that renders the React tree into the browser DOM (`createRoot`). React core knows nothing about the DOM, which is why these are two packages. |

### Development tools (`devDependencies`)

| Package | Why |
|---|---|
| `vite` | Dev server with instant HMR plus the production build. Understands TypeScript and CSS Modules out of the box — so no Webpack, no Babel, no separate CSS loader. |
| `@vitejs/plugin-react` | Adds JSX support and Fast Refresh to Vite (component state survives a file save). |
| `typescript` | The compiler and the type server. Vite only strips types during the build and never checks them, so `tsc --noEmit` in the `build` script is the actual type check. |
| `@types/react`, `@types/react-dom` | React's types: without them `useState<Task[]>`, event types and prop types don't infer. |
| `eslint` | Static analysis: catches bugs and questionable code before you run it. |
| `typescript-eslint` | The parser plus the rules that understand TypeScript (plain ESLint cannot read `.ts`/`.tsx`). |
| `eslint-plugin-react-hooks` | The hooks rules — they catch the most common real React bugs: a conditionally called hook, a missing `useEffect` dependency. |
| `eslint-plugin-react-refresh` | Warns about exports that break Fast Refresh in dev. |
| `prettier` | Formatting: consistent quotes, indentation, line breaks. Style stops being a decision. |
| `eslint-config-prettier` | Turns off the ESLint formatting rules that conflict with Prettier. Clear split of duties: ESLint for bugs, Prettier for looks. |
| `globals` | The set of global names (`window`, `document`, …) for the ESLint config, so they aren't reported as undeclared variables. |

Deliberately **not** included: Redux / Zustand (a single `useState` in `App` is enough), react-router (one page), any UI kit (CSS Modules per the requirements), `uuid` (the built-in `crypto.randomUUID()` is enough).

## Implementation steps

### 1. Scaffold the project

The directory isn't empty (`.git`, `README.md`, `diary.md`), so scaffold in place:

```powershell
npm create vite@latest . -- --template react-ts
npm install
```

Then remove the template leftovers: `src/App.css`, `src/assets/react.svg`, `public/vite.svg`, and the demo contents of `App.tsx` and `index.css`.

### 2. Prettier and ESLint

Install: `npm i -D prettier eslint-config-prettier`

`.prettierrc`:

```json
{
  "semi": true,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "all"
}
```

In `eslint.config.js` (already generated by the Vite template) add `eslintConfigPrettier` as the **last** entry of the config array so it overrides the conflicting rules.

Scripts in `package.json`:

```json
"scripts": {
  "dev": "vite",
  "build": "tsc --noEmit && vite build",
  "preview": "vite preview",
  "lint": "eslint .",
  "format": "prettier --write \"src/**/*.{ts,tsx,css}\""
}
```

### 3. Types — `src/types.ts`

```ts
export interface Task {
  id: string;
  text: string;
  completed: boolean;
}

export type Filter = 'all' | 'active' | 'completed';
```

`Filter` is a union rather than `string` so TypeScript can check the filtering `switch` for exhaustiveness and reject a typo passed as a prop.

### 4. The `src/hooks/useLocalStorage.ts` hook

A generic hook: `useLocalStorage<T>(key: string, initialValue: T): [T, Dispatch<SetStateAction<T>>]`.

- The initial value is read **lazily** through the `useState(() => …)` initializer, so `localStorage.getItem` + `JSON.parse` run once on mount instead of on every render.
- The read is wrapped in `try/catch`: if storage holds corrupted JSON (hand-edited, or an old format), return `initialValue` instead of breaking the app with a blank screen.
- The write happens in a `useEffect` on value change: `localStorage.setItem(key, JSON.stringify(value))`.

All storage access is isolated here, so the components know nothing about `localStorage`.

### 5. `src/App.tsx` — state and logic

The single owner of state (lifting state up):

```ts
const [tasks, setTasks] = useLocalStorage<Task[]>('todo-tasks', []);
const [filter, setFilter] = useState<Filter>('all');
```

The filter is **not** persisted to localStorage — it's view state, not user data.

Handlers (all using the functional update form `setTasks(prev => …)`, never mutating the array):

- `addTask(text: string)` — trim whitespace, ignore an empty string; the new task is `{ id: crypto.randomUUID(), text, completed: false }`;
- `deleteTask(id: string)` — `prev.filter(t => t.id !== id)`;
- `toggleTask(id: string)` — `prev.map(t => t.id === id ? { ...t, completed: !t.completed } : t)`.

The filtered list is derived with `useMemo` over `[tasks, filter]`.

Markup: `<h1>`, `<TaskForm onAdd={addTask} />`, `<TaskFilters current={filter} onChange={setFilter} />`, `<TaskList … />`.

### 6. Components

All of them are function components typed with an `interface Props`, with no state they don't need.

- **`TaskForm`** — a controlled `<input>` with local `useState` for the text, inside `<form onSubmit>` (submit rather than `onClick`, so Enter works). The input clears after a successful add.
- **`TaskFilters`** — three buttons rendered from a constant `FILTERS: { value: Filter; label: string }[]`. The active button gets an extra class via `` `${styles.button} ${isActive ? styles.active : ''}` ``. Accessibility: `aria-pressed={isActive}`.
- **`TaskList`** — takes `tasks`, `onToggle`, `onDelete`. When the array is empty it renders an empty-state message (worded per the active filter); otherwise a `<ul>` of `TaskItem`s with `key={task.id}`.
- **`TaskItem`** — an `<li>` with `<input type="checkbox" checked={task.completed} onChange={…}>`, the task text (a completed one gets a class with `text-decoration: line-through` and a muted color), and a delete button with `aria-label={`Delete task: ${task.text}`}`.

### 7. Styles

- `src/index.css` — globals only: `box-sizing: border-box`, margin reset, system font stack, color CSS variables on `:root`.
- Everything else lives in a `*.module.css` next to its component, imported as `import styles from './X.module.css'`. Class names in camelCase (`styles.deleteButton`) so they can be accessed without bracket notation.
- Look and feel: a centered card at `max-width: 480px`, tidy spacing, a visible `:focus-visible` ring on every interactive element.

### 8. `.gitignore`

The Vite template already generates a suitable one (`node_modules`, `dist`, logs) — review it and extend if needed.

   - delete a task — it disappears from the list;
   - "Active" shows only unchecked tasks, "Completed" only checked ones, "All" shows everything;

   - delete every task → the empty-state message appears.

5. DevTools → Console — clean, no errors and no React warnings.
